# 50%限制：main 版本 system prompt 規則

> 可折疊區塊格式，貼到 Notion 後可依主題收合。內容依 2026-10-22 的 main 整理；每段 prompt 的完整原文在 `docs/main_prompts.md`。

<details>
<summary><strong>目的</strong></summary>

main 是「LLM 自由規劃」的版本：用哪幾塊方塊、圖形擺在桌上哪裡、格距多大、動作順序與高度，都由 LLM 自己決定。系統只提供設備事實與執行介面，不給擺放區、補貨區，也不告訴 LLM 手臂的可達範圍。LLM 的輸出在送到 Unity / UR3e 之前，仍要經過程式的格式與安全檢查。

</details>

<details>
<summary><strong>整體原則</strong></summary>

- LLM 不可輸出 URScript、關節角、速度、加速度或 I/O 指令。
- LLM 只能用 6 個高階函式：`move_above`、`descend`、`grasp`、`release`、`lift`、`wait`；位置參數只能寫 `source` 或 `target`。
- 系統只給設備事實（座標慣例、方塊尺寸、桌面範圍、手臂基座、夾爪尺寸、介面），不給擺放區、補貨區、手臂可達範圍。
- 每一層都做 deterministic check（轉譯、執行前檢查、Unity 路徑檢查），不只靠 LLM 遵守 prompt。
- 相機只在任務開始拍一次；之後每一輪都用同一張照片與同一份場景。
- 每個任務最多 10 輪；失敗後由 LLM 反思寫成「暫定規則」，交給下一輪。
- 手臂執行到一半失敗時，桌面已經變了，任務直接結束。

</details>

<details>
<summary><strong>階段 1：平面／立體判斷</strong></summary>

- 只依指令本身判斷：2d = 積木只有一層、從正上方看；3d = 積木往上疊、立起來。
- 不分類動作、不給支援的動作清單，程式也沒有關鍵字規則。
- 輸出 JSON：`dimension`（2d / 3d）與 `reason`。

</details>

<details>
<summary><strong>階段 2：圖案設計限制</strong></summary>

**共通**
- 顏色由程式決定：指令有提到就用該顏色，否則用桌上比較多的顏色。
- 庫存 = 桌上那個顏色的全部方塊（main 沒有補貨區）。
- prompt 明寫不提供字型、範本、目標專屬規則或範例圖；以人眼辨識為優先。
- 畫不出可辨識且做得到的圖形時，要回傳不可行（feasible=false），不可硬湊。
- 設計失敗時，這個任務直接記為失敗，不進入規劃。

**2D bitmap**
- 最多 5 × 5，每列等長，只能包含 `0` / `1`。
- cube 佔 1 格、domino 佔 2 個相鄰格；需要的格數不能超過庫存。

**3D 高度圖**
- 固定 1 排 × 3 欄 × 3 層，只用 cube。
- 每個數字是那一欄從桌面往上疊幾塊，不可懸空、不可中空。
- 從正面讀：+Z 朝上、桌面在底、+X 由左到右；不可為了做得到而旋轉、鏡射或倒過來。

**雙模型審查**
- OpenAI 與 Gemini 各畫一張候選。
- 互相審查對方的候選：2D 可附修改版；3D 審正面方向是否正確。
- 通過的候選匿名投票：OpenAI 權重 0.80、Gemini 權重 0.20。
- 只剩一張候選時，加權分數要達 0.50 才採用。
- 最多 2 回合；第 2 回合附上對方的審查意見。
- 3D 投票訊息會說明候選圖是「疊起來的方塊從正面看」。
- Unity 關閉「pattern審查」時，只請 OpenAI 畫一次，仍保留本地格式與庫存檢查。

</details>

<details>
<summary><strong>階段 3：拆解限制</strong></summary>

- 角色：「你是 UR3 機械手臂的任務控制者。根據使用者目標與目前觀測，自行規劃並完成任務。」
- 第 2 輪起，system prompt 後面附上累積的暫定規則；不衝突的舊規則有效，衝突時新規則優先。
- 提供：目標、目前場景（每個物件的 index 與座標）、上次結果、座標與方向詞、方塊尺寸、桌面範圍與手臂基座、圖形驗收、字母規範（2D）或正面判讀（3D）、設計好的目標 bitmap、相機照片。
- 不提供：執行介面、夾爪尺寸、計畫格式。
- 提醒：場景 index 只代表這一張清單的位置，不能當成跨輪次的物件身分。
- 輸出：自然語言的子任務說明，交給規劃階段。

</details>

<details>
<summary><strong>階段 4：規劃限制</strong></summary>

- 角色與暫定規則同拆解；環境事實也相同。
- 執行介面：`move_above(location, height_m)`、`descend(location)`、`grasp()`、`release()`、`lift(location, height_m)`、`wait(seconds)`。
- 參數範圍：height_m 0.05～0.15 m（端點上方的距離）；seconds 0.1～3 s。
- target 的 Z 是方塊放好後的頂面高度。
- 不提供任意 XY 偏移、條件分支或同輪失敗續跑；每輪只能交一條確定的動作路徑。
- 不得自行加入 `go_home`；整批完成後由執行器在安全時回 Ready / Home。
- 夾爪事實：
  - 張開內側約 3.5 cm，夾 cube 時兩指落在 ±X 兩側；
  - 手指厚、寬各約 1.5 cm；
  - 閉合方向上相鄰的 cube，中心要相距約 4.5 cm 以上；
  - 只能夾上方沒有東西的物件。
- 每輪都要寫出每個 target 的實際 (x, y, z)，不能只寫「沿用上一輪」之類的代號。
- 計畫格式：在「執行路徑開始」與「執行路徑結束」之間，每組抓放先寫一行「source index N → target (x, y, z)」，下面緊接著這一組的函式呼叫，再寫下一組。
- 附一個低階操作範例，標明「僅示範介面語意，不是固定解法」。

**排圖形時**
- 2D 字母：每個字母最多 5 × 5 格，固定格距（要讓手指放得下），每格一塊 cube，像 5×5 點陣字。
- 方向以相機畫面為準：畫面上方是 +Y、右方是 +X，不可上下或左右顛倒。
- 3D 改用正面判讀：從 -Y 那側看，往右 +X、往上 +Z。
- 有目標 bitmap 時：照 bitmap 排，不自己重新設計；同方向固定格距；排在桌面空著的地方。
- 執行前會檢查排出的圖形跟 bitmap 完全相同，不同就不執行。

</details>

<details>
<summary><strong>階段 5：轉譯與執行前檢查（不是 LLM）</strong></summary>

**轉譯**
- 本地程式照字面轉換，不替 LLM 選物件、目標或動作。
- 每組抓放最多 20 個函式；失敗訊息不寫上限數字。
- `source index` 與 target 的配對數必須跟動作組數一致。

**執行前檢查（csharp_server）**
- 來源與目標要在工作區內：X −0.025～0.805 m、Y −0.025～0.475 m。
- 檢查移動高度、跟其他方塊的間距、搬運距離、函式白名單。
- 排出的圖形要等於目標 bitmap（去掉四周空白後逐格相同）。

**Unity 手臂檢查**
- 取料離手臂底座 0.20～0.47 m；放置 0.16～0.47 m。
- 檢查逆運動學是否有解、自身碰撞、撞桌、奇異點、底座方向。
- 移到上方時先試算往下放得下去嗎，放不下去才換另一組手臂姿勢（不影響原本就能走的路徑）。
- 2D 在 Unity 預覽；3D 送 URSim 並由 Isaac Sim 做物理模擬。

**回饋給 LLM 的方式**
- 以上範圍都不告訴 LLM。
- 失敗時只回報出事的座標與原因，由下一輪自己修正。

</details>

<details>
<summary><strong>階段 6：模擬畫面判定限制</strong></summary>

- 2D 在 Unity 畫面重疊率 > 90% 之後判定；3D 在 Isaac 物理檢查與重疊率都通過之後判定。
- 獨立驗證者：不帶暫定規則，看不到計畫與目標 bitmap，只看原始指令、初始與模擬後的場景、模擬畫面。
- 判準：檢查整體目標與局部幾何（直線、連接、堆疊）；座標偏差 2 cm 內可接受。
- 用積木排的圖形當點陣字看：同方向固定格距，格子之間的空隙不算斷開。
- 3D 以正面判讀：從 -Y 那側看，不能左右或上下顛倒。
- 沒有足夠證據或目標含糊時不可通過。
- 第一行 `PASS` 才送實體手臂（純模擬直接算完成）；`FAIL` 的理由交給反思。

</details>

<details>
<summary><strong>階段 7：反思限制</strong></summary>

- 角色：「你是 UR3 機械手臂的任務控制者，負責分析這一輪的結果。」
- 只規定輸出格式：第一行 `GIVE_UP`（放棄任務）或 `CONTINUE`（繼續下一輪）。
- 第二行起寫什麼完全由 LLM 決定。
- 提供：本輪計畫、轉譯結果、系統回饋、最新場景、環境與介面事實、夾爪事實、字母規範或正面判讀、目標 bitmap、既有規則。
- `CONTINUE` 的內容會累積成新版暫定規則，加到之後每一輪的拆解、規劃、反思。

</details>

<details>
<summary><strong>LLM 看得到的設備事實</strong></summary>

- 座標：QR 座標以公尺為單位，X / Y 在桌面上、Z 向上；物件 Z 是頂面高度。
- 方向詞：+X = 左、-X = 右、+Y = 後、-Y = 前、+Z = 上、-Z = 下；依 QR 座標解讀，不依相機畫面。
- 尺寸：cube 0.025 m；domino 0.05 × 0.025 × 0.025 m。
- 桌面：QR1～QR4 圍成的矩形，X 0～0.805 m、Y 0～0.371 m。
- 手臂基座在 QR (0.390, 0.363)。
- 圖形驗收：圖形要排在空的地方，跟沒用到的積木明顯分開，能單獨被辨認。

</details>

<details>
<summary><strong>已知問題（尚未修改）</strong></summary>

- 規劃 prompt 有兩句過時描述：「每個操作開始前系統會重新觀測來源物件位置」、「執行失敗後由下一輪根據新觀測重規劃」。
- 驗證者的「連接」與「2 公分」是寫死的判準，曾讓格距較大的圖形被判 FAIL。
- 夾爪事實裡的「中心要相距約 4.5 cm 以上」是算好的答案，反思常直接照抄。
- 低階範例的固定數字（例如抬升 0.12）可能被沿用。
- 拆解看不到介面規定，曾把位置寫成座標，導致轉譯連續失敗。
- 位置寫成座標時，轉譯器回報的是「函式數超過上限」，沒有說到真正的錯誤。
- 可達範圍不給 LLM，Unity 的退回訊息又偏技術用語，LLM 不容易知道該往哪個方向修。

</details>
