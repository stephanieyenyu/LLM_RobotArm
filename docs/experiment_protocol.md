# 自由規劃與失敗反思實驗

目前主流程為：自然語言子任務拆解 → 自然語言操作計畫 → 忠實轉譯 → 執行前檢查 → 模擬驗證（2D：Unity；3D：URSim＋Isaac Sim；畫面重疊率＋LLM 看模擬畫面）→ 實機執行；未通過就全新獨立嘗試、不使用 Reflection（2026-10-08 起；之前是執行後用相機做局部及整體驗證）。原本的固定任務分類、bitmap 設計、布局實現和派工流程已移除。

## 驗證流程（2026-10-08 起，三個版本相同）

main、zero-constraint、rulebased 三個版本用同一套驗證流程與純模擬場景。相機（純模擬：虛擬場景）只在收到指令時讀一次場景、照片與相機位姿，之後的驗證都看模擬畫面，執行後不再拍照驗證。

- 2D：整批先在 Unity 模擬（只預覽，手臂不動），預覽結束拍俯視畫面跟預期格（原始 bitmap 映射到 LLM 寫的 bitmap_grid；沒有時用計畫畫出的 bitmap）比畫面重疊率（同 main：只拍方塊、1 mm 一格、Σ min ÷ Σ max，要大於 90%），通過後由獨立的結果驗證者（LLM）看 Unity 主相機的模擬畫面與預覽後的場景判 PASS，兩關都過才把同一批送實體手臂（不再預覽）。純模擬時 Unity 模擬驗證通過就算執行完成，模擬世界照預覽落點更新，不需要 Isaac Sim。這個版本由 LLM 給 TCP 姿態：2D 用 Unity 本地 IK（UR3eKinematics，同 main、rulebased）解，不用開 URSim；3D 照舊由 URSim 的 get_inverse_kin 解。在這之前 2D 也由 URSim 解 IK；兩個 IK 都從上一個姿勢找最近的解，但數值解與控制器的解析解在選哪一組解、靠近奇異點時能不能解出來可能不同，2D 結果跟之前不宜直接比較。規劃 prompt 的「URSim 負責 IK，不要提供關節角度」與「URSim 依此姿態自動計算關節 IK」同時改成「執行器負責 IK…」「執行器依此姿態…」，其餘文字不變。之前的覆蓋率比對（方塊蓋住格子中心才算那格有方塊）與「比對通過就結束、不送手臂」已移除。
- 3D：Unity 不預覽，只把同一套關節軌跡轉送 URSim；Isaac Sim 跟隨 URSim 做物理，跑完做物理檢查（位置、層高、傾斜、撞動、穩定、指尖撞桌、手臂自撞）、畫面重疊率與 LLM 看 Isaac 畫面判 PASS，全部通過才把同一批送實體手臂（純模擬送 URSim；驗證前後 Isaac 的積木位姿用 snapshot／restore 還原）。畫面重疊率用 Isaac 量到的積木位姿投影成 1 mm 一格的俯視高度圖（層數 = 頂面高度 ÷ 0.025 取整），跟預期高度圖（原始高度圖映射到 bitmap_grid 的每一層；沒有時用計畫的高度圖）比 Σ min ÷ Σ max；先把整個圖形在 ±5 mm 內平移對齊再算，要大於 90%。對齊是因為 Isaac 的物理落點常整體偏約 2 mm，不對齊時放對也只有約 85%；對齊只容許整體平移，離線測試中少一層（80%）、多一塊（88.7%）、轉 8°（89.1%）仍不通過。
- 驗證者的 system prompt 不變；user 訊息裡原本的「附圖是目前實際相機畫面」換成說明附圖是 Unity 或 Isaac 的模擬畫面（ExperimentLlm.UnityImageNote／IsaacImageNote）。
- 驗證未通過記為 simulation 失敗，實機不動，直接全新獨立嘗試（不使用 Reflection、不限次數）。全部通過、手臂（純模擬：模擬）做完就算成功；執行後沒有整體驗證，global_validation 不再出現。手臂執行到一半失敗（execution）時桌面已改變，又不再重新拍照，這個任務直接結束。
- 純模擬的場景只剩兩個，三個版本的檔案完全相同：yellow_cubes_15（預設；15 塊黃方塊 5 欄 × 3 排，中心間距 6 cm，X 0.08～0.32、Y 0.06～0.18）與 domino_cube（一塊橫放的黃 domino 在 (0.20, 0.10)、一塊黃方塊在 (0.12, 0.18)）；run_mode.json 指定的場景檔不存在時改用預設場景。
- 在這之前：2D 用覆蓋率比對，通過就結束、不送手臂；3D 先在 Unity 預覽逐層比對高度圖，Isaac 只做物理檢查與畫面判定，送實機前再檢查來源積木有沒有被移動超過 1 cm；純模擬的 2D 也送 URSim 執行；純模擬場景是 two_cubes、letter_blocks、domino_cubes。兩段時期的結果不應直接比較。

## 啟動與重置

先啟動 perception_server 與 Unity，在 csharp_server 目錄執行 `dotnet run`。需要 OPENAI_API_KEY；ROBOT_MODEL 可指定模型，預設 gpt-5。Unity 仍使用既有輸入與執行檔案介面。

預設每個任務以收到指令時的桌面為起點：相機連續三次看到桌面穩定（跟上一幀一對一比對名稱、形狀、XY 15mm、Z 10mm，domino 另比方向與角度）就開始，當下的場景存成該任務的 `initial_scene.json`。各任務的起點因此可能不同，跨任務比較成功率時要一併報告起點配置（每個任務的 config.json 記 `initial_scene_source = table_at_command`）。

需要每個任務都從同一個配置開始時（正式比較用），設定環境變數 `FIXED_BASELINE=1` 後重啟服務：第一次任務建立 `outputs/experiments/initial_scene.json`，之後每個新任務都必須將實體積木放回該配置，未符合就等待並逐物件列出差距（config.json 記 `fixed_baseline`）。兩種模式都不會用虛擬積木重置冒充實體桌面重置，也不會自動操控手臂搬回積木。更換固定基準需停止服務，移除 initial_scene.json，再建立新基準。

同一任務內不重置積木；下一次嘗試接續上次結果，重新觀測並規劃。規則只在本任務內存在，下一個任務清空。Unity 的執行前動畫預覽仍會還原預覽前的畫面；這是撤銷虛擬預演，不是撤銷實體操作。實機仍沿用既有 Ready/Home、碰撞與關節檢查；收尾 Ready/Home 路徑只在安全檢查通過時執行，否則停在最後的安全抬升位置，不否定已完成的抓放。系統並未要求 LLM 學習低階關節控制。

## 輸出與迭代

兩個規劃層只輸出自然語言，不要求模型填寫 JSON、bitmap 或固定任務 schema。C# 的確定性 adapter 只辨識模型已明確寫出的來源、數值目標與白名單函式，不呼叫另一個 LLM，也不補上解題決策、抓放順序或目的座標；缺少必要決定就判定轉譯失敗（算一輪、進 Reflection，見下方失敗類型）。內部 JSON 僅供 C# 與 Unity 通訊。自然語言原文和本地轉譯結果均保存，供人工稽核。

2026-10-01 起轉譯由這個本地 adapter 做：規劃文字每組抓放要寫成「source index N → target (x, y, z)」，函式呼叫逐行列在「執行路徑開始」與「執行路徑結束」之間。adapter 依 source index 複製來源物件的名稱、形狀與方向，只換成計畫寫的 x、y（有寫 z 才換 z），所以 domino 的方向一律沿用來源，目前 LLM 沒辦法讓 domino 轉向（之前的 LLM 轉譯器可以填 target 的 orientation）。更早之前名稱與形狀也交給 LLM 轉譯器填時，它把「放在哪個物件上」誤填成身分，11 次嘗試全被執行前檢查擋下、手臂未動，該批結果量到的是轉譯錯誤而非推理能力，不應與之後的成功率直接比較。

給規劃與反思的回饋只提供事實與能力邊界，不提供解法：執行前檢查的錯誤訊息寫明違反的欄位、實際值與欄位定義，不寫應填的值；每輪附上系統紀錄的實際流程（走到哪一關、在哪一關停止、實體手臂完整執行了幾個操作）與轉譯結果，反思不可把紀錄以外的步驟寫成觀測事實；設備能力說明包含參數範圍（height_m 0.05～0.15 m、seconds 0.1～3、每個操作最多 20 個函式、同一操作內依序執行且無中途感知或條件分支）與夾爪幾何（平行雙指張開時內側只有約 3.5 cm，只跨得住 2.5 cm 寬的邊、跨不住 domino 長邊；每根手指厚、寬各約 1.5 cm，手指下降時閉合方向兩側各只剩約 5 mm，外側離物件中心約 3.25 cm，碰到這個範圍內的旁邊物件；只能夾最上層）。張開寬度與手指尺寸是 2026-09-30 實測值。

2026-10-01 起 prompt 不再定義擺放區（TargetZone）：拆解、規劃、整體驗證、反思都不提擺放區，放置位置完全由 LLM 依目標與場景決定；程式本來就不檢查放置位置是否在擺放區內。在這之前，目標沒指定位置時 prompt 要求放進擺放區（先是 25 個格點，之後只給範圍），這兩段時期的結果不應與之後直接比較。目標若提到「擺放區」或「黃色區域」，現在的 prompt 沒有定義它在哪裡；Unity 畫面上的藍色補貨區與黃色擺放區也一併拿掉，桌面只剩白色桌板與 QR1～QR4。改為提供桌面範圍（QR1～QR4 圍成的矩形）、手臂基座位置與可達距離（2026-10-01 用規劃器掃整張桌面：目標離基座 0.20～0.48 m 全部規劃得到），以及排圖形的驗收條件：圖形排在空著的地方、跟沒用到的物件明顯分開、能單獨辨認；規劃、反思與整體驗證看到的是同一句。

系統不提供 placed/holding 任務分類，也不規定抓放順序。是否在步驟結束時保持夾持，依模型實際輸出的 grasp/release 狀態推導；若仍夾持，Unity 不執行批次結尾的 Ready/Home。規劃介面不提供 go_home：每一批完成後，收尾路徑通過安全檢查時由執行器經 Ready 回 Home，不通過就停在最後的安全抬升位置，不否定已完成的抓放（2026-10-01 起；之前收尾路徑不通過會整批退回）。規劃與反思的 prompt 都說明不得加入 go_home；本地轉譯器只辨識 move_above、descend、grasp、release、lift、wait，計畫裡的 go_home 或其他函式會被略過、不會執行。Unity 執行器仍認得 go_home，最後一個手臂動作是 go_home 時不再執行收尾的 Ready/Home（從 Home 規劃收尾路徑必定被奇異點檢查擋下）；go_home 後面若還有動作，從 Home 出發的下一段一定規劃失敗。安全層只檢查硬體能力、參數範圍、工作區、碰撞間隙及當下危險狀態，結果驗證則直接對照原始目標。

3D 疊放批次的 descend 高度由執行層依場景結構換算：指尖停在積木真實頂面下 12.5 mm（積木高度正中間，2026-10-10 起；之前是 19 mm）；真實頂面取「感知 z 對齊 2.5 cm 層高」與「佔地重疊的下層 + 1 層」的較高者，同一批前面步驟放下的積木也算。LLM 的 target.z 只能把放開高度往上調，不會讓夾爪壓進支撐。這是執行器把指令換成實際高度的物理換算，不寫進任何 prompt，也不替 LLM 選來源、XY、方向或動作順序。2D 批次維持原本的「感知頂面 + Z_CORRECTION」。2026-09-29 之前的 3D 結果受舊下降深度影響（指尖停在積木頂面上方，URSim 跑完積木都沒被夾起），量到的是執行層問題，不應與之後的成功率直接比較。

2026-10-10 起實機 3D 放置可以開「碰到就停」（Unity JsonExecutor 的 `contactStopOnPlace`，預設關）：最後 10 mm 以 10 mm/s 往下，Z 受力超過 8 N 就停下放開，最多降到計算高度。不寫進 prompt，也不改來源、XY、方向、順序或層高；URSim、Isaac 驗證與 Unity 預覽不受影響。打開後實機因為擠壓下層失敗的情況會減少，開啟前後的實機結果不宜直接比較；三個版本比較時要用同一個設定。這一版的 prompt 寫明「每個 TCP 點都是你的決定，程式不改方向、不補抬升或中間避障點」；打開碰到就停時，執行器會在 LLM 給的放置點上方多停一個點、也可能停在比它高的位置，是這個原則的例外，要記在實驗紀錄裡。

3D 的正式執行是把通過 URSim／Isaac 驗證的同一批整批送出（同樣的步驟、來源位置與積木高度，關節軌跡跟驗證時相同），步驟之間不重新觀測、不做局部驗證，由整體驗證判定；送出前若來源積木在驗證後移動超過 1 cm 就不執行，記為 precheck 失敗。2026-09-30 之前的 3D 是逐步執行，每一步結束回 Ready 的收尾路徑沒有經過驗證。2026-10-08 起不再檢查來源積木在驗證後有沒有移動，Isaac 驗證另外比畫面重疊率（見上方「驗證流程」）。

2D 從 2026-10-01 起也整批：所有步驟包成一批，Unity 先預覽整批，模擬結束跟計畫畫出的 bitmap 比對，重疊率（放對的格數 ÷（預期格數 + 圖案範圍內多出來的格數），cube 一格、domino 兩格）要大於 90% 才整批送實機；不通過實機完全不動，記為 simulation 失敗。步驟之間不重新觀測、不做局部驗證，由整體驗證判定；2D 的夾取深度與參數不變。bitmap 由程式依計畫放下的物件畫出（跟相機畫面同方向：上 = +Y、右 = +X；同一塊搬兩次只算最後的位置），跟比對結果一起印在 csharp_server 的 terminal，也存在每一輪的 sim_check.json；LLM 不輸出 bitmap，也沒有第二個模型審查。之前的 2D 逐步執行，每一步前重新觀測、執行後局部驗證。2026-10-08 起比對改用 main 的畫面重疊率，通過後還要由 LLM 看 Unity 的模擬畫面判 PASS 才送實機，執行後不再做整體驗證（見上方「驗證流程」）。

排字母的規範（2026-10-01 起）：prompt 要求每個字母設計在最多 5×5 的方格上（每個方向固定格距、格距要讓手指放得下），筆畫要像 5×5 點陣字一樣能辨識，字母以相機畫面判讀（上方 = +Y、右方 = +X），不能上下或左右顛倒。bitmap 的 X、Y 格距分開推算（同一排相鄰物件間距的中位數），目標是排字母時（獨立的大寫英文字母，或寫了「字母」），畫出來超過每個字母 5×5 格（多個字母並排時寬度另加字母之間最多 2 格）就不送 Unity，記為 precheck 失敗。能不能辨識由整體驗證看畫面判定，沒有另外的模型審查 bitmap。

執行前檢查另外依步驟順序檢查放置目標有沒有跟同一層的積木部分重疊（同一批前面步驟放下的也算，每邊容許 2 mm）；重疊超過較小那塊佔地一半的照原本的規則當成疊放，交給 3D 流程。

夾爪方向 2026-09-30 起依實測修正：張開只有 3.5 cm，domino 一律跨短邊夾（橫放 domino 的夾爪轉 90°），之前的程式讓手指沿 domino 長邊開合，實機夾不起 domino；Isaac 的夾爪開度也從 7 cm 改成 3.5 cm，之前 Isaac 驗證的手指會撞到 5 cm 內的旁邊積木。同一天 Isaac 的手指也從資產模型（指尖厚 21 mm、寬 20 mm，碰撞體是凸包，外側離夾爪中心 38.5 mm）換成實測的 15 mm × 15 mm 直方塊（外側離中心 32.5 mm），prompt 的夾爪說明也補上手指尺寸。這之前含 domino 的結果與 Isaac 驗證結果不應與之後直接比較。

一次嘗試包含一份拆解與操作計畫；轉譯失敗、執行前拒絕、局部不通過、整體不通過都耗用一次，最多十次，不含額外隱藏規劃重試。每次未達標都生成失敗摘要與暫定規則，逐輪累積在下一輪 system prompt 的任務經驗區（標版本、由舊到新）；不衝突的舊規則持續有效，新證據推翻舊規則時由新規則明確指出取代哪一條。反思第一行寫 CONTINUE 或 GIVE_UP，只有明確的物理不可能證據才寫 GIVE_UP，該任務就提早結束。第十次失敗也保存反思，但不再執行。

局部驗證沿用物件來源／目的位置、顏色、形狀及堆疊觀測。整體驗證為獨立模型呼叫，僅看原始目標、初始／目前觀測與相機畫面，不看規劃者的答案或規則。第一行 PASS/FAIL 是評分介面，不是規劃格式限制。2026-10-08 起整體驗證改在送手臂之前做，看的是模擬畫面（2D：Unity；3D：Isaac）與模擬後的場景，執行後不再拍照驗證。沒有影像、沒有物件或局部失敗不能算成功。

目前整體幾何與圖案辨識由視覺模型評估，尚非經人工標註校準的正式量測；論文實驗應先固定驗收標準並人工盲評檢查其可靠性。原有堆疊驗證包含遮蔽／合併輪廓推論，局部通過仍不能獨立證明堆疊高度。

## 純模擬

Unity 的「模式」按鈕可切成純模擬：場景與照片來自 Isaac Sim，初始桌面是虛擬場景檔（sim_scenes/*.json），2026-10-08 起 2D 只在 Unity 模擬驗證（畫面重疊率＋LLM 看 Unity 畫面），通過就算執行完成、模擬世界照預覽落點更新，不連 URSim；3D 送 URSim，Isaac 跟隨 URSim 讓積木依物理移動（之前所有動作都送 URSim）。prompt、轉譯、執行前檢查、局部與整體驗證、反思都跟實機相同，config.json 記 run_mode = sim。純模擬沒開 Isaac Sim 時（任務開始連不到 Isaac），2D 改用 csharp_server 內建的虛擬世界：起點是場景檔，2D 整批通過 Unity 模擬驗證後，照預覽的落點更新（2026-10-08 之前是 URSim 執行完成後照計畫移到 target）；沒有物理，積木不會被推動、碰撞或傾倒；給 LLM 的畫面是依座標畫的俯視示意圖，prompt 會說明那不是照片。3D 疊放需要 Isaac 做物理驗證，遇到時任務停止並記為 infrastructure_error。每個任務用的是 Isaac 還是內建虛擬世界記在 sim_backend.txt；內建虛擬世界的結果比 Isaac 更樂觀，兩者不應混在一起比較。切到純模擬或換場景的當下，Unity 會先把場景檔載入 Isaac 並顯示，這只是預覽與重設模擬世界；任務開始時 csharp_server 仍依 reset_each_task 重建，任務起點不受影響。任務進行中不要切換或換場景，否則會重設模擬世界。純模擬的紀錄與 metrics.json 放在 outputs/experiments_sim，不計入實機成功率：模擬回報的是精確位置，沒有相機的偵測誤差、遮擋與高度偏差，成功率會偏樂觀，只能用來測規劃能力或事先排除明顯不可行的任務。

## 紀錄與指標

每個任務的獨立資料夾包含 task、config、initial_scene、每輪所有 system/user prompt、原始文字、轉譯結果、前後場景、相機圖、逐步執行／局部驗證、整體判定、反思、每輪的 attempt_result.json、模型 token 用量與 result.json。每次任務結束時更新 outputs/experiments/metrics.json，統計首次／十次內成功率、逐次累積成功率與各失敗類型的次數。

result.status 為 success、failed（十次內未達標）、infrastructure_error 或 execution_unknown（2026-09-30 之前的紀錄另有 adapter_error）。轉譯失敗算一輪任務失敗並進入 Reflection：本地轉譯器在計畫裡找不到明確的來源 index、數值 target 或函式呼叫、抓放組數跟配對數對不起來，或單批超過 50 個操作。2026-10-01 之前轉譯器是 LLM，另包含 JSON 解析、必要欄位、型別與函式白名單錯誤。API／相機故障記為 infrastructure_error，不進入 Reflection。

每一輪的 attempt_result.json 記錄 failure_kind，result.json 的 attempt_outcomes 依序列出每輪結果（success 或失敗類型），metrics.json 的 attempt_outcome_counts 統計全部任務各類型的次數，分析時可把轉譯失敗與規劃／執行失敗分開：planning（在拆解或規劃階段就停止）、translation_format（轉譯結果不符合執行介面，例如超過 50 個操作；2026-10-01 之前也包含 LLM 轉譯器的輸出讀不懂）、translation_rejected（本地轉譯器找不到明確的來源、數值 target 或函式，或配對不起來）、precheck（執行前檢查拒絕）、simulation（3D 的 URSim 執行、Isaac Sim 幾何檢查或模擬畫面判定未通過，或 2D 的 Unity 預覽 bitmap 比對未通過）、execution（Unity／實體手臂執行失敗）、local_validation（局部驗證未通過，只出現在 2026-10-01 之前逐步執行的 2D）、global_validation（全部執行完成但整體判定未達標）。2026-10-08 起 simulation 也包含 2D 的 Unity 模擬畫面判定與 3D 的 Isaac 畫面重疊率未通過；global_validation 不再出現；execution 之後任務直接結束。Unity 執行逾時代表狀態未知，停止服務，不會再送重試或 done；必須人工確認手臂停止後重啟。

主要指標：十次內達標任務數／有效任務數。另報首次成功率、各次累積成功率、成功所需嘗試數、呼叫量和耗時。基礎設施錯誤和執行未知需另外完整報告，不可挑選性刪除。所有判定是模型評分，需經人工稽核再用於正式研究。
