# 自由規劃與失敗反思實驗

目前主流程為：自然語言子任務拆解 → 自然語言操作計畫 → 忠實轉譯 → 執行前檢查 → Unity／實機執行 → 局部及整體驗證 → 失敗反思與 prompt 更新。原本的固定任務分類、bitmap 設計、布局實現和派工流程已移除。

## 目標 bitmap 設計（2026-10-02 起，沿用 release 260917 的 PatternDesigner）

每個任務確認初始桌面後、第一輪規劃前，都先用 release 260917 的 PatternDesigner 畫目標 bitmap，prompt 與檢查原封不動（只加了把每次呼叫存進 design/ 的紀錄，以及沒有 GEMINI_API_KEY 也能啟動）。不分類指令：沒有 CommandRouter，也沒有「支援哪些動作」之類的規則。OpenAI 與 Gemini 各自畫一張最多 5×5 的 0/1 bitmap，再各自審查對方的圖（可附修改版）；被對方接受的圖與合格的修改版進入決選，不只一張時兩個模型匿名打分，OpenAI 佔 80%、Gemini 佔 20%，最多 2 輪。Unity 的「pattern審查」關掉時（StreamingAssets/skip_pattern_review.txt = 1）只請 OpenAI 畫一次直接採用。

顏色照舊版 GuessBlockColor（指令提到黑或黃就用它，否則用桌上較多的顏色），庫存是桌上那個顏色的所有 cube 與 domino（現在沒有補貨區，也不排除抓不到的方塊）。選出的 bitmap 放進拆解、規劃與反思的 prompt，要求照它排；每一輪轉譯完，計畫排出的圖形（去掉四周空白）要跟目標逐格相同，不同就記為 precheck 失敗、手臂不動。畫不出可用的圖時任務記為失敗（attempts = 0，result.json 的 design_error 記原因），算進成功率；要交叉審查卻沒有 GEMINI_API_KEY、或 Gemini 回傳 HTTP 錯誤時記為基礎設施錯誤。每次呼叫的 prompt 與回覆存在任務資料夾的 design/，結果存成 design.json。整體驗證仍然只看原始指令，不看設計的 bitmap。

## 啟動與重置

先啟動 perception_server 與 Unity，在 csharp_server 目錄執行 `dotnet run`。需要 OPENAI_API_KEY；ROBOT_MODEL 可指定模型，預設 gpt-5。Unity 仍使用既有輸入與執行檔案介面。

預設每個任務以收到指令時的桌面為起點：相機連續三次看到桌面穩定（跟上一幀一對一比對名稱、形狀、XY 15mm、Z 10mm，domino 另比方向與角度）就開始，當下的場景存成該任務的 `initial_scene.json`。各任務的起點因此可能不同，跨任務比較成功率時要一併報告起點配置（每個任務的 config.json 記 `initial_scene_source = table_at_command`）。

需要每個任務都從同一個配置開始時（正式比較用），設定環境變數 `FIXED_BASELINE=1` 後重啟服務：第一次任務建立 `outputs/experiments/initial_scene.json`，之後每個新任務都必須將實體積木放回該配置，未符合就等待並逐物件列出差距（config.json 記 `fixed_baseline`）。兩種模式都不會用虛擬積木重置冒充實體桌面重置，也不會自動操控手臂搬回積木。更換固定基準需停止服務，移除 initial_scene.json，再建立新基準。

同一任務內不重置積木；下一次嘗試接續上次結果，重新觀測並規劃。規則只在本任務內存在，下一個任務清空。Unity 的執行前動畫預覽仍會還原預覽前的畫面；這是撤銷虛擬預演，不是撤銷實體操作。2026-10-01 起模擬與實機各動一次：Unity 的手臂只在預覽時動，URSim 或實體手臂執行期間 Unity 的手臂與方塊都不動，整批結束才對齊實機最後的姿勢；3D 的正式執行跟 URSim 驗證那批同一條軌跡，不再預覽。在這之前，執行期間 Unity 的手臂會跟著實機再動一次，夾爪同步還會把畫面上的方塊夾著走；純模擬沒開 Isaac 時，整批中途失敗後 Unity 畫面上的方塊可能跟內建虛擬世界不一致（之後的預覽出現夾取落空，比對卻因為目標位置已經有方塊而通過）。實機仍沿用既有 Ready/Home、碰撞與關節檢查；收尾 Ready/Home 路徑只在安全檢查通過時執行，否則停在最後的安全抬升位置，不否定已完成的抓放。系統並未要求 LLM 學習低階關節控制。

## 輸出與迭代

兩個規劃層只輸出自然語言，不要求模型填寫 JSON、bitmap 或固定任務 schema。C# 的確定性 adapter 只辨識模型已明確寫出的來源、數值目標與白名單函式，不呼叫另一個 LLM，也不補上解題決策、抓放順序或目的座標；缺少必要決定就判定轉譯失敗（算一輪、進 Reflection，見下方失敗類型）。內部 JSON 僅供 C# 與 Unity 通訊。自然語言原文和本地轉譯結果均保存，供人工稽核。

2026-10-01 起轉譯由這個本地 adapter 做：規劃文字每組抓放要寫成「source index N → target (x, y, z)」，函式呼叫逐行列在「執行路徑開始」與「執行路徑結束」之間。adapter 依 source index 複製來源物件的名稱、形狀與方向，只換成計畫寫的 x、y（有寫 z 才換 z），所以 domino 的方向一律沿用來源，目前 LLM 沒辦法讓 domino 轉向（之前的 LLM 轉譯器可以填 target 的 orientation）。更早之前名稱與形狀也交給 LLM 轉譯器填時，它把「放在哪個物件上」誤填成身分，11 次嘗試全被執行前檢查擋下、手臂未動，該批結果量到的是轉譯錯誤而非推理能力，不應與之後的成功率直接比較。

給規劃與反思的回饋只提供事實與能力邊界，不提供解法：執行前檢查的錯誤訊息寫明違反的欄位、實際值與欄位定義，不寫應填的值；每輪附上系統紀錄的實際流程（走到哪一關、在哪一關停止、實體手臂完整執行了幾個操作）與轉譯結果，反思不可把紀錄以外的步驟寫成觀測事實；設備能力說明包含參數範圍（height_m 0.05～0.15 m、seconds 0.1～3、每個操作最多 20 個函式、同一操作內依序執行且無中途感知或條件分支）與夾爪幾何（平行雙指張開時內側只有約 3.5 cm，只跨得住 2.5 cm 寬的邊、跨不住 domino 長邊；每根手指厚、寬各約 1.5 cm，手指下降時閉合方向兩側各只剩約 5 mm，外側離物件中心約 3.25 cm，碰到這個範圍內的旁邊物件；只能夾最上層）。張開寬度與手指尺寸是 2026-09-30 實測值。

2026-10-02 起，反思的 prompt 只規定輸出格式：第一行 GIVE_UP 或 CONTINUE，第二行起寫什麼由 LLM 自己決定，這些內容會累積交給之後的規劃與反思。原本的寫作規定全部拿掉，包括：區分事實與假設、規則要來自本輪證據、2 cm 內的偏差不算失敗、取代舊規則要說明、不能用代號、什麼情況才能 GIVE_UP 等。設備介面、參數範圍與夾爪幾何改成環境事實照樣提供。在這之前的反思有這些規定，前後結果不應直接比較。

2026-10-01 起 prompt 不再定義擺放區（TargetZone）：拆解、規劃、整體驗證、反思都不提擺放區，放置位置完全由 LLM 依目標與場景決定；程式本來就不檢查放置位置是否在擺放區內。在這之前，目標沒指定位置時 prompt 要求放進擺放區（先是 25 個格點，之後只給範圍），這兩段時期的結果不應與之後直接比較。目標若提到「擺放區」或「黃色區域」，現在的 prompt 沒有定義它在哪裡；Unity 畫面上的藍色補貨區與黃色擺放區也一併拿掉，桌面只剩白色桌板與 QR1～QR4。改為提供桌面範圍（QR1～QR4 圍成的矩形）、手臂基座位置與可達距離（2026-10-01 用規劃器掃整張桌面：目標離基座 0.20～0.48 m 全部規劃得到），以及排圖形的驗收條件：圖形排在空著的地方、跟沒用到的物件明顯分開、能單獨辨認；規劃、反思與整體驗證看到的是同一句。2026-10-02 起不再給手臂可達距離：prompt 只給桌面範圍與手臂基座位置，純模擬的俯視示意圖也不畫可達範圍的圓弧；到不到得了由執行前檢查與 Unity 判斷，LLM 只能從失敗的回饋得知；系統產生的失敗訊息也不再附可達範圍的數字（只說來源或目標超出手臂可達範圍、工作區或太靠近底座，並附出問題的座標，完整數字只記在 Unity Console）。反思時 LLM 自己從失敗推出的規則照常保留。2026-10-01～10-02 的結果有給可達距離，不應與之後直接比較。

系統不提供 placed/holding 任務分類，也不規定抓放順序。是否在步驟結束時保持夾持，依模型實際輸出的 grasp/release 狀態推導；若仍夾持，Unity 不執行批次結尾的 Ready/Home。規劃介面不提供 go_home：每一批完成後，收尾路徑通過安全檢查時由執行器經 Ready 回 Home，不通過就停在最後的安全抬升位置，不否定已完成的抓放（2026-10-01 起；之前收尾路徑不通過會整批退回）。規劃與反思的 prompt 都說明不得加入 go_home；本地轉譯器只辨識 move_above、descend、grasp、release、lift、wait，計畫裡的 go_home 或其他函式會被略過、不會執行。Unity 執行器仍認得 go_home，最後一個手臂動作是 go_home 時不再執行收尾的 Ready/Home（從 Home 規劃收尾路徑必定被奇異點檢查擋下）；go_home 後面若還有動作，從 Home 出發的下一段一定規劃失敗。安全層只檢查硬體能力、參數範圍、工作區、碰撞間隙及當下危險狀態，結果驗證則直接對照原始目標。

3D 疊放批次的 descend 高度由執行層依場景結構換算：指尖停在積木真實頂面下 19 mm；真實頂面取「感知 z 對齊 2.5 cm 層高」與「佔地重疊的下層 + 1 層」的較高者，同一批前面步驟放下的積木也算。LLM 的 target.z 只能把放開高度往上調，不會讓夾爪壓進支撐。這是執行器把指令換成實際高度的物理換算，不寫進任何 prompt，也不替 LLM 選來源、XY、方向或動作順序。2D 批次維持原本的「感知頂面 + Z_CORRECTION」。2026-09-29 之前的 3D 結果受舊下降深度影響（指尖停在積木頂面上方，URSim 跑完積木都沒被夾起），量到的是執行層問題，不應與之後的成功率直接比較。

3D 疊放從 2026-10-01 晚上起也做 Unity 畫面比對：3D 的 bitmap 是俯視高度圖（每格是那格最上面的積木在第幾層，例如站起來的 L 是 3 1 1），含壓在底下沒被搬的支撐；URSim 驗證那批在 Unity 預覽結束時用同一套逐層切開的畫面重疊率比對，大於 90% 才讓 URSim 動，不通過 URSim、實機都不動，記為 simulation 失敗；通過後照舊由 URSim／Isaac 做物理驗證。Unity 預覽沒有物理，疊不穩、撞倒旁邊積木仍靠 Isaac 抓。3D 的正式執行是把通過 URSim／Isaac 驗證的同一批整批送出（同樣的步驟、來源位置與積木高度，關節軌跡跟驗證時相同），步驟之間不重新觀測、不做局部驗證，由整體驗證判定；送出前若來源積木在驗證後移動超過 1 cm 就不執行，記為 precheck 失敗。2026-09-30 之前的 3D 是逐步執行，每一步結束回 Ready 的收尾路徑沒有經過驗證。

2D 從 2026-10-01 起也整批：所有步驟包成一批，Unity 先預覽整批，模擬結束跟計畫畫出的 bitmap 比對，重疊率要大於 90% 才整批送實機。從 2026-10-01 晚上起，重疊率是畫面重疊率：預覽結束、場景還原前，用正上方的正交相機只拍方塊（不拍手臂、桌面、QR 標記），重新取樣成跟 bitmap 同方向、1 像素 = 1 mm 的格子，並逐層切開拍（第 k 張只留比第 k 層中間高的部分）得到每一點疊幾層，跟預期佔地（cube 2.5×2.5 cm、domino 5×2.5 cm，已在目標 2 公分內不搬的物件放在它實際的位置）比：重疊率 = Σ min(實際層數, 預期層數) ÷ Σ max(實際層數, 預期層數)，2D 全是 1 層時就是像素的交集 ÷ 聯集，疊到別塊上也會扣分，範圍是預期佔地的外框四邊各加半格；比對圖存成每一輪的 sim_check.png（三格：Unity 俯視畫面 / 預期 / 疊合，csharp_server 在上方標出重疊率與 PASS/FAIL）。這比原本嚴格得多：預覽的落點就在 TCP 正下方，放對時接近 100%，一塊偏 2 mm 那塊只剩約 85%。在這之前用的是座標比對的格子重疊率（放對的格數 ÷（預期格數 + 圖案範圍內多出來的格數），cube 一格、domino 兩格，落點離預期 2 cm 內算放對），現在只當說明，跟錯誤清單一起給反思；不通過實機完全不動，記為 simulation 失敗。步驟之間不重新觀測、不做局部驗證，由整體驗證判定；2D 的夾取深度與參數不變。bitmap 由程式依計畫放下的物件畫出（跟相機畫面同方向：上 = +Y、右 = +X；同一塊搬兩次只算最後的位置），規劃回覆轉譯完就印在 csharp_server terminal 的 LLM 進度後面（後面的檢查沒過也看得到；3D 疊放逐層畫，只畫這一輪搬動的積木），比對結果另外印出，也存在每一輪的 sim_check.json；LLM 不輸出 bitmap，也沒有第二個模型審查。之前的 2D 逐步執行，每一步前重新觀測、執行後局部驗證。

排字母的規範（2026-10-01 起）：prompt 要求每個字母設計在最多 5×5 的方格上（每個方向固定格距、格距要讓手指放得下），筆畫要像 5×5 點陣字一樣能辨識，字母以相機畫面判讀（上方 = +Y、右方 = +X），不能上下或左右顛倒。bitmap 的 X、Y 格距分開推算：物件中心在各軸上分成一列一列，相鄰兩列的距離（8 cm 以內）是候選，取最大、又能讓七成五以上物件落在格點上的那個。2026-10-01 修正前用的是同一排相鄰物件間距的中位數，遇到 Z 的斜筆畫（每列只有一塊）或 H 的橫槓（只有一列有相鄰物件）會量成兩倍格距，把兩列併成一列，那之前的 bitmap 與 sim_check.json 可能少一列或一行。目標是排字母時（獨立的大寫英文字母，或寫了「字母」），畫出來超過每個字母 5×5 格（多個字母並排時寬度另加字母之間最多 2 格）就不送 Unity，記為 precheck 失敗。能不能辨識由整體驗證看畫面判定，沒有另外的模型審查 bitmap。

執行前檢查另外依步驟順序檢查放置目標有沒有跟同一層的積木部分重疊（同一批前面步驟放下的也算，每邊容許 2 mm）；重疊超過較小那塊佔地一半的照原本的規則當成疊放，交給 3D 流程。

夾爪方向 2026-09-30 起依實測修正：張開只有 3.5 cm，domino 一律跨短邊夾（橫放 domino 的夾爪轉 90°），之前的程式讓手指沿 domino 長邊開合，實機夾不起 domino；Isaac 的夾爪開度也從 7 cm 改成 3.5 cm，之前 Isaac 驗證的手指會撞到 5 cm 內的旁邊積木。同一天 Isaac 的手指也從資產模型（指尖厚 21 mm、寬 20 mm，碰撞體是凸包，外側離夾爪中心 38.5 mm）換成實測的 15 mm × 15 mm 直方塊（外側離中心 32.5 mm），prompt 的夾爪說明也補上手指尺寸。這之前含 domino 的結果與 Isaac 驗證結果不應與之後直接比較。

一次嘗試包含一份拆解與操作計畫；轉譯失敗、執行前拒絕、局部不通過、整體不通過都耗用一次，最多十次，不含額外隱藏規劃重試。每次未達標都生成失敗摘要與暫定規則，逐輪累積在下一輪 system prompt 的任務經驗區（標版本、由舊到新）；不衝突的舊規則持續有效，新證據推翻舊規則時由新規則明確指出取代哪一條。反思第一行寫 CONTINUE 或 GIVE_UP，只有明確的物理不可能證據才寫 GIVE_UP，該任務就提早結束。第十次失敗也保存反思，但不再執行。

局部驗證沿用物件來源／目的位置、顏色、形狀及堆疊觀測。整體驗證為獨立模型呼叫，僅看原始目標、初始／目前觀測與相機畫面，不看規劃者的答案或規則。第一行 PASS/FAIL 是評分介面，不是規劃格式限制。沒有影像、沒有物件或局部失敗不能算成功。

目前整體幾何與圖案辨識由視覺模型評估，尚非經人工標註校準的正式量測；論文實驗應先固定驗收標準並人工盲評檢查其可靠性。原有堆疊驗證包含遮蔽／合併輪廓推論，局部通過仍不能獨立證明堆疊高度。

## 純模擬

Unity 的「模式」按鈕可切成純模擬：場景與照片來自 Isaac Sim，初始桌面是虛擬場景檔（sim_scenes/*.json）。2026-10-02 起，純模擬的 2D 由 Unity 預覽與 bitmap 比對完成就算執行，不連 URSim 也不連實體手臂：手臂可達範圍等幾何限制跟實機同一套，在預覽前對整批檢查；預覽結束時方塊的實際落點寫回模擬世界（內建虛擬世界直接改位置，開著 Isaac 時重新載入成落點，沒有物理過程），再照常做整體驗證決定 success。沒有 UR 控制器（不會保護性停機）也沒有物理，結果比實機樂觀。3D 疊放仍送 URSim，由 Isaac 跟隨 URSim 讓積木依物理移動並驗證。在這之前純模擬的 2D 也要送 URSim 執行，沒開 URSim 時整批記為 execution 失敗（「UR 未連線」）。prompt、轉譯、執行前檢查、局部與整體驗證、反思都跟實機相同，config.json 記 run_mode = sim。純模擬沒開 Isaac Sim 時（任務開始連不到 Isaac），2D 改用 csharp_server 內建的虛擬世界：起點是場景檔，2D 整批通過 Unity 預覽的 bitmap 比對後，照預覽的落點更新；沒有物理，積木不會被推動、碰撞或傾倒；給 LLM 的畫面是依座標畫的俯視示意圖，prompt 會說明那不是照片。3D 疊放需要 Isaac 做物理驗證，遇到時任務停止並記為 infrastructure_error。每個任務用的是 Isaac 還是內建虛擬世界記在 sim_backend.txt；內建虛擬世界的結果比 Isaac 更樂觀，兩者不應混在一起比較。切到純模擬或換場景的當下，Unity 會先把場景檔載入 Isaac 並顯示，這只是預覽與重設模擬世界；任務開始時 csharp_server 仍依 reset_each_task 重建，任務起點不受影響。任務進行中不要切換或換場景，否則會重設模擬世界。純模擬的紀錄與 metrics.json 放在 outputs/experiments_sim，不計入實機成功率：模擬回報的是精確位置，沒有相機的偵測誤差、遮擋與高度偏差，成功率會偏樂觀，只能用來測規劃能力或事先排除明顯不可行的任務。

## 紀錄與指標

每個任務的獨立資料夾包含 task、config、initial_scene、每輪所有 system/user prompt、原始文字、轉譯結果、前後場景、相機圖、逐步執行／局部驗證、整體判定、反思、每輪的 attempt_result.json、模型 token 用量與 result.json。每次任務結束時更新 outputs/experiments/metrics.json，統計首次／十次內成功率、逐次累積成功率與各失敗類型的次數。

result.status 為 success、failed（十次內未達標）、infrastructure_error 或 execution_unknown（2026-09-30 之前的紀錄另有 adapter_error）。轉譯失敗算一輪任務失敗並進入 Reflection：本地轉譯器在計畫裡找不到明確的來源 index、數值 target 或函式呼叫、抓放組數跟配對數對不起來，或單批超過 50 個操作。2026-10-01 之前轉譯器是 LLM，另包含 JSON 解析、必要欄位、型別與函式白名單錯誤。API／相機故障記為 infrastructure_error，不進入 Reflection。

每一輪的 attempt_result.json 記錄 failure_kind，result.json 的 attempt_outcomes 依序列出每輪結果（success 或失敗類型），metrics.json 的 attempt_outcome_counts 統計全部任務各類型的次數，分析時可把轉譯失敗與規劃／執行失敗分開：planning（在拆解或規劃階段就停止）、translation_format（轉譯結果不符合執行介面，例如超過 50 個操作；2026-10-01 之前也包含 LLM 轉譯器的輸出讀不懂）、translation_rejected（本地轉譯器找不到明確的來源、數值 target 或函式，或配對不起來）、precheck（執行前檢查拒絕）、simulation（3D 的 URSim 執行、Isaac Sim 幾何檢查或模擬畫面判定未通過，或 2D 的 Unity 預覽 bitmap 比對未通過）、execution（Unity／實體手臂執行失敗）、local_validation（局部驗證未通過，只出現在 2026-10-01 之前逐步執行的 2D）、global_validation（全部執行完成但整體判定未達標）。Unity 執行逾時代表狀態未知，停止服務，不會再送重試或 done；必須人工確認手臂停止後重啟。

主要指標：十次內達標任務數／有效任務數。另報首次成功率、各次累積成功率、成功所需嘗試數、呼叫量和耗時。基礎設施錯誤和執行未知需另外完整報告，不可挑選性刪除。所有判定是模型評分，需經人工稽核再用於正式研究。
